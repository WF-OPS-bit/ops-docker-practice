# 部署排障实录

本文记录两个项目在真实环境（CentOS 7 虚拟机 + Docker 26.1.4）部署过程中**实际遇到的问题**，以及定位和解决的全过程。

文中的报错都是原始输出，解法都在仓库里落地了。

---

## 写在前面

**环境**

| 项 | 值 |
|---|---|
| 宿主机 | Windows（开发、打包、推送 GitHub） |
| 服务器 | VMware 虚拟机，CentOS Linux 7 (Core) |
| Docker | 26.1.4 + Docker Compose v2.27.1 |
| 内存 | 3.7 G（可用约 900M，另有 4G swap 分区） |

**最终结果**

| 项目 | 验证 |
|---|---|
| 项目二：Nginx + Docker Compose 集群 | 五项验证全 PASS |
| 项目三：MySQL GTID 主从 + Redis 哨兵 | 四项验证全 PASS（含真实故障转移） |

**为什么单独写这份文档**

这两套配置的"跑通"只占工作量的一小部分，绝大部分时间花在排查上。而排查过程恰恰是最有含金量的部分——它证明你真的动手了，并且知道自己在做什么。

## 一、环境与传输

### 1.1 GitHub SSH 推送被拒：22 端口被劫持

**现象**

```text
$ ssh -T git@github.com
git@github.com: Permission denied (publickey).
```

加了公钥后重试，错误变成：

```text
banner exchange: Connection to UNKNOWN port -1: Connection refused
```

**排查**

第二个报错很关键——它不是鉴权失败，是**连接根本没建立**。直接测端口：

```powershell
(New-Object System.Net.Sockets.TcpClient).Connect("github.com", 22)
# github.com:22=FAIL ... 127.0.0.1:22
```

**根因**

`github.com:22` 被解析到了 **`127.0.0.1:22`**——本机代理软件或 hosts 文件劫持，SSH 走 22 端口永远出不去。

第一个报错（Permission denied）是因为 TCP 还能到；第二个（Connection refused）是彻底不通。**同一个根因、两种报错**，很容易误判成"网络不稳定"或者"公钥没配好"。

**解法**

GitHub 提供 SSH over 443 的备用通道。不需要改 `~/.ssh/config`，直接把 remote 写成带端口的 URL：

```bash
git remote add origin ssh://git@ssh.github.com:443/WF-OPS-bit/ops-docker-practice.git
```

验证：`ssh -T -p 443 git@ssh.github.com` 返回 `Hi WF-OPS-bit!` 即通。

> 顺带：在 GitHub 网页建仓库时，**README / .gitignore / license 三个初始化选项必须全留空**。否则远端有一个初始 commit，与本地历史无关，push 会被拒。

### 1.2 CentOS 无法 clone GitHub

**现象**

```text
正克隆到 'ops-docker-practice'...
致命错误：无法访问 'https://github.com/...'：TCP connection reset by peer
```

**根因**

虚拟机所在网络访问 GitHub 被重置。注意这与 1.1 不同：宿主机 Windows **能**访问 GitHub（所以能 push），但 CentOS **不能**。

**解法**

代码本来就在 Windows 上，直接绕开网络：

```powershell
# Windows 侧打包
tar -czf ops-docker-practice.tar.gz ops-docker-practice
```

再用 Xftp（或 `scp`）传到 CentOS 的 `/root/`，解压即可。后续所有"补 README、commit、push"都在 Windows 侧完成。

> 这个分工后来形成了固定流程：**服务器只负责跑验证，文档和推送在 Windows 侧做。**

### 1.3 vim 报 E325：发现交换文件

**现象**

```text
E325: 注意
发现交换文件 ".env.swp"
进程 ID: 18108 (仍在运行)
以只读方式打开([O]), 直接编辑((E)), 恢复((R)), 退出((Q)), 中止((A)):
```

**判断**

关键看两行：

- `修改过: 否` → 交换文件里**没有**未保存内容，杀进程不会丢东西
- `进程 ID: 18108 (仍在运行)` → 选 `E` 会让两个 vim 同时写一个文件，风险很大

所以按 `Q` 退出，回 shell 处理：

```bash
ps -o pid,tty,stat,cmd -p 18108
kill 18108
rm -f .env.swp
```

**后续改进**

`.env` 只有 5 行，用 heredoc 一次写完，彻底不碰 vim：

```bash
cat > .env <<'EOF'
MYSQL_ROOT_PASSWORD=RootPwd2026abc
MYSQL_DATABASE=appdb
MYSQL_USER=appuser
MYSQL_PASSWORD=AppPwd2026abc
REDIS_PASSWORD=RedisPwd2026abc
EOF
```

`<<'EOF'` 的**单引号不能省**，它保证内容原样写入、不被 shell 展开变量。

### 1.4 `.env` 丢失，compose 变量全部为空

**现象**

```text
WARN[0000] The "MYSQL_USER" variable is not set. Defaulting to a blank string.
WARN[0000] The "MYSQL_PASSWORD" variable is not set. Defaulting to a blank string.
...
✘ Container project2-compose-nginx-mysql-1  Error
dependency failed to start: container ... mysql-1 is unhealthy
```

MySQL 容器一直 `Restarting`。

**根因（两层）**

1. **直接原因**：`.env` 文件不存在。之前 vim 卡在 E325 没写成，加上后来重新解压过目录，文件彻底没了。`.env` 被 `.gitignore` 排除，**不在分发包里**，删目录就会丢。
2. **连带原因**：MySQL 官方镜像在既没有 `MYSQL_ROOT_PASSWORD`、也没允许空密码时会**直接拒绝启动**（exit 1）。于是 `depends_on: condition: service_healthy` 永不满足，整条链路卡死。

**解法**

重建 `.env`，然后**必须清掉脏状态**：

```bash
docker compose down -v     # -v 连 volume 一起删
docker compose up -d
```

**为什么要 `-v`**：MySQL 的 root 密码只在数据目录为空（首次初始化）时写入。用空密码启动失败后，卷里留下的是半初始化的脏目录；不删的话下次启动 MySQL 认为"已初始化过"，跳过密码设置——你会看到容器起来了，但用新密码怎么都连不上，比现在更难查。

> 通用结论：**改过 `.env` 里的密码，就要 `down -v`。**

## 二、项目二（Nginx + Docker Compose）

### 2.1 容器内 DNS 解析失败，Maven 构建中断 ★

这是整个过程中耗时最长的一个坑。

**现象**

```text
=> ERROR [web1 build 4/6] RUN mvn -B dependency:go-offline
[FATAL] Non-resolvable parent POM ... Could not transfer artifact
org.springframework.boot:spring-boot-starter-parent:pom:3.1.12
from/to central (https://repo.maven.apache.org/maven2):
repo.maven.apache.org: Temporary failure in name resolution
```

**排查（走了弯路）**

第一反应是"国外 Maven 源连不上"，于是加了阿里云镜像。结果报错变成：

```text
Could not transfer artifact ... from/to aliyun-public
(https://maven.aliyun.com/repository/public):
maven.aliyun.com: Temporary failure in name resolution
```

**换了个域名还是解析失败** —— 这一下暴露了真相：问题不在仓库地址，在 DNS 本身。

**根因**

宿主机的 `/etc/resolv.conf` 是：

```
nameserver 192.168.117.2
```

这是 **VMware NAT 网关**的地址。宿主机自己用它没问题，但 Docker 容器（源地址在 `172.17.0.0/24`）发出的 DNS 查询要经过二次 NAT 才能到达这个网关，而这类虚拟网关的 DNS 代理通常不处理这种流量——**容器内所有域名解析全部失败**。

**为什么极具迷惑性**：`docker pull` 是完全正常的。因为拉镜像是 **Docker daemon 在宿主机上**发起的，走 `registry-mirrors`，跟容器 DNS 毫无关系。于是你会误以为"网络没问题"。

**解法（三层，全部采纳）**

1. **给 Docker daemon 配公共 DNS**（根治）

   ```json
   {
     "registry-mirrors": ["https://你的加速地址"],
     "dns": ["223.5.5.5", "114.114.114.114"]
   }
   ```

   改完 `systemctl restart docker`。⚠️ **别把原来的 `registry-mirrors` 弄丢了**，否则连镜像都拉不动。

2. **构建阶段用宿主机网络**（不依赖 daemon 配置）

   ```yaml
   build:
     context: ./app
     network: host
   ```

   host 模式下容器与宿主机共享网络栈，DNS 查询等于宿主机自己发的，不再有二次 NAT 问题。这条作用于**所有构建阶段**，运行阶段里那句 `apt-get install curl` 也一并受益。

3. **Maven 源指向阿里云**（提速，国内必做）

   新增 `app/maven-settings.xml`，由 Dockerfile `COPY` 进 `/root/.m2/settings.xml`。`mirrorOf` 只写 `central` 不写 `*`，避免劫持将来可能声明的私有仓库。

**排查口诀**

容器网络出问题，第一步永远是看**容器内部**看到什么：

```bash
docker run --rm --entrypoint cat nginx:1.27-alpine /etc/resolv.conf
docker run --rm --entrypoint nslookup nginx:1.27-alpine maven.aliyun.com
```

两条就能区分"DNS 坏了"和"目标站不通"。

### 2.2 `check.sh` 误报 FAIL：GNU sed 不补换行

**现象**

验证明明是成功的，脚本却报 FAIL：

```text
===== 验证 1：加权负载均衡（weight=2:1，期望约 4:2） =====
连续请求 6 次 /api/hi：
1 279a3e27bbbb8d2602a8f425279a3e27bbbb279a3e27bbbb8d2602a8f425279a3e27bbbb
[FAIL] 只命中了一个实例 —— 检查 Nginx upstream 和容器网络
```

**解读输出**

那串乱码其实是 6 个 hostname 粘在一起。拆开看：

```
279a3e27bbbb  ← web1
8d2602a8f425  ← web2
279a3e27bbbb
279a3e27bbbb
8d2602a8f425
279a3e27bbbb
```

**web1 命中 4 次、web2 命中 2 次——正好是 `weight=2:1`，负载均衡完全正常。**

**根因（两个行为叠加）**

1. Spring Boot 返回的响应体**末尾没有换行符**
2. **GNU sed 处理"最后一行无换行"的输入时，输出也不补换行**

于是 6 次 `curl | sed` 的结果被拼成一整串，`uniq -c` 只统计到 1 行，判定"只命中一个实例"。

**解法**

循环里每次提取后自己补一个换行：

```bash
counts=$(for _ in $(seq 1 6); do
  curl -s http://localhost/api/hi | sed -n 's/.*"instance":"\([^"]*\)".*/\1/p'
  echo          # ← 补这个
done)
```

> 通用结论：任何 `curl | sed` 循环计数的场景都要注意这一点。

### 2.3 内存不足：先问"被谁占了"

**现象**

`free -h` 显示可用只剩 900M 左右，担心起不动。

**排查**

两条命令结论完全不同：

```bash
docker stats --no-stream     # 容器视角
ps aux --sort=-%mem | head   # 系统视角
```

结果出人意料——五个容器加起来才 **916 MB**，而容器之外有两笔大开销：

```text
mysql   2614  /usr/sbin/mysqld              467 MB   ← 系统里原生装的 MySQL
stu     3196  /usr/bin/gnome-shell          220 MB   ← GNOME 桌面
stu     3562  /usr/bin/gnome-software       117 MB
root    1866  /usr/bin/X :0                  80 MB   ← 合计约 420 MB
```

**结论**：**容器里同时跑着两个 MySQL**（一个原生安装的，一个容器里的），外加一整套图形界面。容器本身一点不胖。

**解法**

按收益排序：停原生 MySQL（470MB）> 关图形界面（420MB）。最终**实测 900M 可用 + 4G swap 足够跑完验证，没有做任何清理**。

**方法论**：内存不够时，第一个问题不是"怎么清理"，而是**"这些内存被谁占了"**。只看 `docker stats` 会让你以为问题在容器里，`ps aux --sort=-%mem` 才能照出容器外那一大块。

## 三、项目三（MySQL GTID 主从 + Redis 哨兵）

### 3.1 MySQL 配置文件权限 777 被静默忽略 ★

**现象**

```text
mysql: [Warning] World-writable config file '/etc/mysql/conf.d/master.cnf' is ignored.
...
ERROR 1777 (HY000) at line 1: CHANGE REPLICATION SOURCE TO
SOURCE_AUTO_POSITION = 1 cannot be executed because @@GLOBAL.GTID_MODE = OFF.
```

**根因**

从 Windows 打出来的 tar 包不保存 Unix 权限位，解压后文件是 `777`。**MySQL 出于安全考虑会拒绝加载"全局可写"的配置文件**——注意它**只打一行 Warning 然后继续正常启动**。

后果是配置里**所有内容都不生效**：不只是 `gtid_mode`，`server_id`、`read_only` 也全都没生效（三个实例 server-id 都是默认的 1）。

**为什么难查**：报错明确指向 GTID，你会一直盯着 GTID 配置看，意识不到是**整个文件被忽略了**。

**解法**

```bash
chmod 644 mysql/*.cnf
docker compose restart mysql-master mysql-slave1 mysql-slave2
```

**打包侧的根治办法**：用 Python `tarfile` 逐项设置权限（目录 755 / `.sh` 755 / 其余 644），重新解压即修复。

> 注意：**Nginx 和 Redis 都不做这项检查**，所以这个坑只会在 MySQL 上暴露。

**方法论**：配置文件"看着对"但行为不对时，先验证它**到底有没有被加载**，而不是反复检查内容：

```bash
SELECT @@server_id, @@gtid_mode, @@read_only;
```

### 3.2 哨兵 `sh: syntax error: unexpected "&&"`

**现象**

```text
redis-sentinel1-1  | sh: syntax error: unexpected "&&"
```

容器一直 `Restarting`。

**根因**

原来的写法：

```yaml
command: >
  sh -c "cp /usr/local/etc/redis/sentinel.conf /tmp/sentinel.conf
         && echo '...' >> /tmp/sentinel.conf
         && redis-sentinel /tmp/sentinel.conf"
```

YAML 的 `>` 确实把三行折成单行，这步没问题。但 **compose 对字符串形式的 `command` 还会再按 shell 规则分词一次**，`&&` 和嵌套引号就在这一步被拆散了。

**最坑的地方**：同一份文件里 `redis-server` 那条 command 用的是**完全相同的写法却能正常工作**——因为它只有空格分隔的参数，没有 `&&`。同一个写法有的能跑有的不能跑，正是这类问题难定位的原因。

**解法**

改用数组形式，`sh -c` 收到完整脚本，不做二次解析：

```yaml
command:
  - sh
  - -c
  - |
    cp /usr/local/etc/redis/sentinel.conf /tmp/sentinel.conf
    echo "sentinel auth-pass mymaster ${REDIS_PASSWORD}" >> /tmp/sentinel.conf
    exec redis-sentinel /tmp/sentinel.conf
```

多行脚本用 `|` 保留换行，三行各自独立，连 `&&` 都不需要。

> 通用结论：compose 里任何带 `&&`、`|`、引号嵌套的 `command` 都应该用数组形式。

### 3.3 Redis 7.4 哨兵解析 master 主机名失败 ★

**现象**

```text
>>> 'sentinel monitor mymaster redis-master 6379 2'
Can't resolve instance hostname.
1:X # Failed to resolve hostname 'redis-master'
*** FATAL CONFIG FILE ERROR (Redis 7.4.11) ***
```

**为什么难查**

同一个网络里，`redis-slave1/2` 用 `replicaof redis-master 6379` **是能正常连上主库的**（`connected_slaves:2`）。也就是说容器名的 DNS 解析本身没问题——你会本能地排除 DNS 方向，转去查权限、查认证，全是错的。

**根因**

**Redis 7.4 的 Sentinel 在加载配置文件阶段就解析 master 主机名**，而 `redis:7-alpine` 用的是 musl libc，其 `getaddrinfo` 行为与 glibc 有差异，这个场景下解析失败就 FATAL 退出（7.2 及更早版本不做这项检查）。

**顺带排除的两个方向**（避免重复劳动）：

- 不是写权限问题：容器实际以 `uid=0(root)` 运行，`/data`、`/tmp` 都可写
- 不是认证问题：`auth-pass` 未生效只会导致哨兵认为主节点不可达，**不会让进程退出**

**解法**

二选一，**本仓库采用方案 1**：

1. **固定 IP** —— compose 用 `ipam` 给 redis-master 分配静态地址，`sentinel.conf` 写这个 IP：

   ```yaml
   networks:
     ha_net:
       driver: bridge
       ipam:
         config:
           - subnet: 172.28.0.0/16
   # redis-master: networks: { ha_net: { ipv4_address: 172.28.0.10 } }
   ```

2. **降级镜像** —— 换 `redis:7.2-alpine`，可继续用容器名。代价是版本不是最新。

> 这个取舍已写入项目三 README 的「已知局限」：**用固定 IP 是兼容性妥协，理想方案应该是容器名。**

### 3.4 哨兵偶发 `Restarting`

**现象**

三个哨兵配置完全相同，其中两个起来了，sentinel2 一直在 `Restarting`。

**判断**

看日志发现它其实在某一次已经成功加载：

```text
Configuration loaded
+monitor master mymaster 172.22.0.5 6379 quorum 2
+slave slave 172.22.0.6:6379
+slave slave 172.22.0.10:6379
+sentinel sentinel ... 172.22.0.8 26379
+sentinel sentinel ... 172.22.0.7 26379
```

**解法**

```bash
docker compose restart redis-sentinel2
```

重启后正常。属于启动时序导致的偶发失败——**配置完全相同的多实例里只有一个失败，通常就是时序问题而不是配置问题**，先重启一次再深挖。

## 四、方法论总结

十条经验，按复用价值排序：

1. **先验证"有没有被加载"，再检查"内容对不对"**
   `SELECT @@变量` 一条就能确认配置文件是否生效。MySQL 那个坑就是栽在"盯着内容看"上。

2. **容器的网络和宿主机的网络是两回事**
   `docker pull` 是 daemon 在宿主机发起的，跟容器 DNS 无关。诊断容器网络，第一步看容器内部的 `/etc/resolv.conf`。

3. **报错换了个目标，不代表病根变了**
   Maven 源从 `repo.maven.apache.org` 换成 `maven.aliyun.com` 后仍然解析失败——恰恰证明了问题在 DNS 而不是仓库地址。

4. **"看起来正常的证据"可能不在出错的路径上**
   redis-slave 用容器名能连主库 ≠ 哨兵也能解析容器名。两者走的是不同的解析路径。

5. **内存/资源问题，先问"被谁占了"**
   `docker stats` 看容器内，`ps aux --sort=-%mem` 看系统全局，两条一起看才完整。

6. **compose 的 `command` 含 `&&` 或引号嵌套 → 用数组形式**
   字符串形式会被二次 shell 分词。

7. **跨系统传输文件时显式设置权限**
   Windows 的 tar 不保存权限位。MySQL 会因 777 静默忽略配置文件。

8. **`depends_on` 不写 `condition: service_healthy` 等于没写**
   容器被创建 ≠ 服务可用。

9. **改过密码就必须 `docker compose down -v`**
   MySQL 密码只在数据目录为空时写入。

10. **改配置前先确认当前状态，别猜**
    `docker compose config --quiet` 校验变量、`SELECT @@变量` 校验生效、
    `docker run --rm --entrypoint nslookup ...` 校验 DNS——这三条能挡掉大部分"改了没生效"的白工。
